## なぜVite4jを作ったのか

BacklogでViteのメジャーバージョンアップ（Vite7からVite8への移行）をしました。その最中に書いたコードを切り出してライブラリ化したのがVite4jです。

https://github.com/nulab/vite4j

正確には、たまたまバグっていなかったコードが、モジュールバンドラーを変えたことで問題として顕在化したので修正が必要になった、というのが正しいです。

## ライブラリの対象利用者

ViteとJavaのテンプレートエンジンを一緒に使う人向けです。2026年現在で一般的な、フロントエンドとバックエンドを完全に分離して開発している人は対象外です。

HTMLがバックエンドのテンプレートエンジンでレンダリングされる場合、次のような流れになります。
1. フロントエンドをViteでビルドする
2. ビルドされた静的ファイルをバックエンド側のリソースディレクトリに配置する
3. バックエンドのテンプレートエンジンから静的ファイルを参照する

バックエンドのテンプレートエンジンから、このビルドされた静的ファイルを読み込む必要があります。しかし、ビルドの出力はハッシュ付きのファイル名になっているため、テンプレートにファイル名を直接書くことができません。

## 手で書くと何が壊れるのか

マニフェストを読む前に、まず手で書いたときに何が起きるかを見ておきます。

先ほどのビルド結果だと、`src/home.jsx`に必要なファイルは`assets/home-CxM2xgA6.js`と`assets/home-4f4nyrQA.css`です。テンプレートにはこう書きたくなります。

```html
<link rel="stylesheet" href="/build/assets/home-4f4nyrQA.css">
<script type="module" src="/build/assets/home-CxM2xgA6.js"></script>
```

ハッシュはビルドのたびに変わるのでそのままでは書けませんが、ファイル名を埋め込む仕組みさえ用意すればここまでは動きます。壊れるのは、バンドラーがチャンクを分割したときです。

`home.jsx`と`admin.jsx`の両方が`Badge`をimportしているので、Viteは`Badge`を共有チャンクとして切り出しました。マニフェストをもう一度見ると、こうなっています。

```json
"_Badge-CVsQWeT6.js": {
  "file": "assets/Badge-CVsQWeT6.js",
  "name": "Badge",
  "css": ["assets/Badge-QUdTYuNx.css"]
},
"src/home.jsx": {
  "file": "assets/home-CxM2xgA6.js",
  "imports": ["_Badge-CVsQWeT6.js"],
  "css": ["assets/home-4f4nyrQA.css"]
}
```

`Badge`のCSSは`src/home.jsx`の`css`には入っていません。`_Badge-CVsQWeT6.js`の`css`に入っています。チャンクは自分のCSSしか並べないので、importしているチャンクを辿らないとそこに届きません。

JSのほうは、ブラウザが`import`を解決して勝手に取りに行ってくれます。しかしCSSは誰も取りに行きません。`manifest[entry].css`だけを見て終わりにすると、`Badge`のスタイルはビルドされ、配信され、どこからもリンクされないまま一度も当たらない、という状態になります。

エラーは出ません。画面が少し崩れるだけです。

## Vite4jの使い方

まず、Vite 側でマニフェストを出すようにします。

```js
// vite.config.js
export default defineConfig({
  build: { manifest: true, rollupOptions: { input: "src/home.jsx" } },
})
```

次に、依存を追加します。

```gradle
implementation 'com.nulab-inc:vite4j:0.1.0'
```

Java 11以降で動きます。Jacksonはoptionalで、使うのは`JacksonManifestParser`だけです。

マニフェストは起動時に1回だけ読みます。

```java
ViteManifest manifest;
try (InputStream in = loader.getResourceAsStream("public/.vite/manifest.json")) {
    manifest = ViteManifest.of(new JacksonManifestParser().parse(in));
}

ViteAssets assets = ViteAssets.builder(manifest)
        .assetUrl(path -> "/build/" + path)
        .build();
```

あとはページごとに、この1行で終わりです。

```java
assets.html("src/home.jsx");
```

戻り値はこうなります。

```html
<link rel="stylesheet" href="/build/assets/Badge-QUdTYuNx.css">
<link rel="stylesheet" href="/build/assets/home-4f4nyrQA.css">
<script type="module" src="/build/assets/home-CxM2xgA6.js"></script>
```

先ほど抜け落ちていた`Badge`のCSSが入っています。順番も、importしたチャンクが先、自分のCSSが後ろで、Viteが`index.html`に書くのと同じです。

## 内部のコア実装

やっていることは、マニフェストのグラフを深さ優先で辿るだけです。

```java
private void walk(String key, Set<String> visited, List<String> css) {
    if (!visited.add(key)) {
        return;
    }
    Chunk chunk = chunks.get(key);
    if (chunk == null) {
        return;
    }
    for (String importee : chunk.imports()) {
        walk(importee, visited, css);
    }
    for (String stylesheet : chunk.css()) {
        if (!css.contains(stylesheet)) {
            css.add(stylesheet);
        }
    }
}
```

肝は、再帰呼び出しが`chunk.css()`の収集より**前**にあることです。importしたチャンクのCSSが先、自分のCSSが後になります。これはモジュールが実行される順番であり、Viteが`index.html`に書き出す順番でもあります。同じセレクタが同じ詳細度で2回宣言されていたら後ろが勝つので、ここを逆にするとViteが出すページと見た目が変わってしまいます。

あとは`visited`で循環を止めるのと、マニフェストにないチャンクは例外にせずスキップするだけです。マニフェストはビルドの出力なので、壊れていてもこちらでは直せません。スタイルが一部当たらないページのほうが、レンダリングに失敗するページよりはマシだと判断しました。

実装は[Viteの公式ドキュメント](https://vite.dev/guide/backend-integration.html)を参考にしました。
